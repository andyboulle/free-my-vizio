## Priority 1 — bugs (fix before moving to the Raspberry Pi)

### R1. App tiles break permanently when the server starts while the TV is unreachable
**Evidence** `src/main.ts`: `device`, `catalog` and `profile` are resolved once at startup
(`const catalog = device ? await loadCatalog(...) : undefined`). If `getDeviceInfo()` fails at boot (TV in deep standby —
observed API outages of ~55 s during standby), `activateShortcut` throws `app is unavailable` for every `app` shortcut
until restart. Reproduced 2026-10-27 with a temp server pointed at `192.0.2.1`. Also: with no `tv.deviceId`, `profile` is
`undefined` and no supervisor is ever created. `/api/admin/catalog` and diagnostics have the same stale-state problem.

**Fix**
1. New `src/tv/device-context.ts` exporting `class DeviceContext` holding `device?: DeviceInfo`, `profile: TvProfile`,
   `verified: boolean`, `catalog: Catalog`.
   - `profile` defaults to `genericSmartCast`; `verified=false` until device info is read.
   - `catalog` is loaded at startup **independently of the TV** via `loadCatalog` (network → cache → fallback), never `undefined`.
   - `async ensureDevice(): Promise<DeviceInfo | undefined>` — if `device` is unset, call `client.getDeviceInfo({timeoutMs:2500})`,
     then set `device`, `profile`, `verified` via `selectProfile`. Concurrent calls share one in-flight promise.
     Failures return `undefined` and are retried on the next call (no permanent failure state).
   - If `config.tv.deviceId` is null after a successful read, store `device.deviceId` in config (`saveConfig`) so rediscovery works.
2. `main.ts`: always create the supervisor when `config.tv.host` is set (profile from the context; `generic` until known).
   Call `ensureDevice()` on startup (don't await) and whenever the supervisor sees `power === 1` and `device` is unset
   (add an optional `onReachable?: () => void` callback to `TakeoverSupervisor` options).
3. `routes-tv.ts` / `routes-admin.ts`: take the `DeviceContext` instead of static `device`/`catalog`/`profile`.
   `activateShortcut` for `kind: 'app'`: `await ctx.ensureDevice()`; if the device is still unknown, resolve the payload with
   `{ chipsetKey: '*', firmware: '' }` semantics (wildcard entry, else the catalog entry's default payload) rather than failing.
4. `/api/admin/diagnostics` reports `profile.id`, `verified`, `model`, `firmware` from the context (live).

**Tests** (`test/unit/device-context.test.ts`, extend `test/integration/server-tv-api.test.ts`)
- TV unreachable at start → `activate('netflix')` after the TV becomes reachable sends `{NAME_SPACE:3, APP_ID:"1"}` (mock TV toggles `unreachable`).
- TV unreachable throughout → activate on an app still attempts a launch with the wildcard/fallback payload and returns 502 only because the TV is unreachable (assert error kind).
- Concurrent `ensureDevice()` → exactly one deviceinfo request.
- Missing `deviceId` → saved after the first successful read.
- Supervisor exists and polls when `deviceId` is null.

**Manual** MT-R1: stop the container, put the TV in standby for ≥ 10 min, start the container, power the TV on with the
remote → our UI appears and Netflix/YouTube tiles launch without restarting the server.

### R2. TV UI focus desynchronises every 30 s and on Back
**Evidence** `web/tv/js/main.js`: `load()` (runs every 30 s and on `visibilitychange`) calls `renderHome()` (rebuilds DOM)
then focuses the first `.tile`, but `pos` keeps the old value. Back focuses the first tile without resetting `pos`.

**Fix**
1. Move focus state into a small pure module `web/tv/js/state.js`: `reconcileFocus(grid, focusedId) → {row, column}` — keeps
   the same shortcut focused after a re-render if it still exists, else the nearest valid position, else `{0,0}`.
2. On refresh: remember the focused `data-id`, skip the DOM rebuild entirely if the new `/api/tv/home` JSON equals the previous
   (`JSON.stringify` compare); otherwise re-render and restore focus via `reconcileFocus`.
3. Back: set `pos = {row:0, column:0}` and focus that tile.
4. Single helper `focusAt(pos)` used everywhere (arrow keys, refresh, Back, initial load).

**Tests** `test/unit/tv-state.test.js`: same id kept after re-render; removed id → nearest neighbour; empty grid → `{0,0}`;
unchanged JSON → no rebuild (pure function `shouldRerender(prev, next)`).
**Manual** MT-R2: focus the 2nd app tile, wait 65 s → still on the same tile; press Right → moves to the correct next tile.
Hide a tile in admin while another is focused → focus stays on the focused tile.

### R3. Offline retries multiply and have no backoff
**Evidence** `web/tv/js/main.js`: on failure `setTimeout(load, Math.min(30000, 1000))` (always 1 s), and the separate
`setInterval(load, 30000)` starts a new 1 s retry chain on each failure → N chains after N×30 s offline.

**Fix** Replace with one scheduler in `web/tv/js/state.js`: `nextDelay(failures) = min(30000, 1000 * 2^failures)`;
a single `scheduleRefresh(delay)` that clears any pending timer before setting a new one; success → `failures=0`, next
refresh in 30 s; `visibilitychange` (visible) → clear timer and load now. Never more than one pending timer or in-flight request.
**Tests** `nextDelay` sequence 1 s, 2 s, 4 s … capped at 30 s; scheduler with a fake timer API never holds > 1 pending timer
across 10 consecutive failures.
**Manual** MT-R3: stop the container for 3 min with the UI open → `docker logs` on restart / server access log shows ≤ ~10
requests from the TV for that period (not hundreds); banner clears within 30 s of restart.

### R4. Stray `}` in the Content-Security-Policy header
**Evidence** live header ends with `base-uri 'none' }` (`src/server/static.ts`, template literal).
**Fix** remove it; move the CSP string to an exported constant `TV_CSP`.
**Test** `test/unit/static.test.ts`: header equals the exact string from ARCHITECTURE §8.5.

## Priority 2 — correctness / robustness

### R5. Catalog falls back to a payload meant for a different chipset
`src/catalog/catalog.ts` `resolvePayload` returns `entry.payload` (= first raw choice, possibly another chipset) when nothing
matches. Per ARCHITECTURE §6.6: return `null` when neither the exact chipset nor `"*"` matches in range, **except** when the
device is unknown (R1 case) → wildcard-or-first. `listAvailableApps` must then omit such apps.
Test with `docs/evidence/catalog/*.sample.json`: Blacknut (MT5586L-only) is **not** listed for `MT5586`; Prime Video resolves
to `{3,"3"}` for `MT5586`/`86.910.19.2-1`.

### R6. Config validation too weak
`validateConfig` only checks `pollMs`. A bad admin PUT (e.g. missing `takeover.loopGuard`) makes every tick throw and shows
as `UNREACHABLE`. Validate all fields of `Config` (types, enums, ranges): `requestTimeoutMs 500–10000`, `confirmDelayMs 0–5000`,
`cooldownMs 0–60000`, `suppressMinutes 0–1440`, `loopGuard.maxLaunches 1–20`, `windowMs 1000–3600000`, `pauseMinutes 1–1440`,
`server.port 1–65535`, `theme ∈ {dark,light,oled}`, `accent` `/^#[0-9a-f]{6}$/i`, `publicBaseUrl` null or `http(s)://` URL,
shortcut `kind`-specific required fields (`app` needs `catalogId` or `payload`; `input` needs `cname`; `system` needs
`action ∈ {native-home, power-off, blank-screen}`), non-empty `label`/`id`/`title`. Table-driven tests for each rule.
Also: if an admin PUT changes `tv.host`/`tv.port`, call `connection.update(...)`.

### R7. `/healthz` misreports reachability
`tvReachable` is derived from takeover state, so `IDLE` (takeover off or not yet polled) reports `true`. Track
`lastTvContactAt` in the supervisor/context (updated on any successful TV response); `tvReachable = now - lastTvContactAt < 10 s`,
`null` if never contacted. Test both cases.

### R8. Admin key endpoint accepts unknown keys
`/api/admin/key` passes any string to `sendKey` → TypeError → 502. Validate against `Object.keys(KEY_CODES)`; unknown → 400.
Test it.

### R9. Rediscovery under Docker Desktop
In bridge mode `pickLanAddress('0.0.0.0')` returns the container address, so the /24 scan targets the Docker network.
Derive the scan base from `config.tv.host` (same /24 as the last known TV address) instead. Document in `docs/DEPLOYMENT.md`
that on Docker Desktop a DHCP reservation for the TV is still recommended. Unit-test the base selection.
